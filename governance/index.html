Reference · Governance · MAYHEM-SPEC-CORE v1.0.0

The rules this site runs on.

The purpose of MAYHEM is to preserve factual continuity, eliminate investigation restart costs, maintain permanent evidence integrity, and provide a structured environment for continuing forensic investigation over time, under direct operator control. Every case on this site - and every automated pass that touches one - is required to follow the rules below.

This page is a public-readable summary of MAYHEM-SPEC-CORE v1.0.0, the complete, canonical specification this site is built to. It leaves out the data-schema and repository-implementation detail that isn't written for a public reader - see the note near the end of this page for what that is and why.

What this investigation is - and isn't

Scope and purpose. §1-3, §5.

Each case, permanently continuable§1-3
This is not a general-purpose research wiki, a public-intelligence dashboard, or a scratch space for notes. Its operational purpose is to maintain forensic investigations while preserving every stage of evidence collection - the repository is the investigation, not a description of it. MAYHEM is a modular mechanism: a repository can run one investigation or several at once, each fully isolated from every other - own evidence, own chronology, own automation state, nothing shared or blended across cases. What's constrained is cross-contamination between unrelated matters and automation quietly broadening a case's own scope, not the number of cases a repository can carry. Every conclusion must remain supported by preserved primary-source evidence - never by inference alone, and never by an investigator's or an automated agent's unsupported assertion.
What this repository will never be§5
Explicitly not: a general intelligence-collection or monitoring platform; an automatic target-generation or mass-investigation-creation system; a heat-score dashboard, ranking system, or public allegation system; an automatic keyword-triggered investigation spawner. None of this machinery runs during routine operation.

Rules that never change

Design principles and architectural constraints. §4, §35-36.

Case Isolation§4
A repository may run one investigation or several concurrently; each is fully isolated from every other (its own evidence, chronology, threads, and automation state) and none share or blend state with another.
Persistent Investigation§4
The investigation never resets; state accumulates, it is not recomputed from scratch each session.
Append-Only Evidence§4
Evidence is never overwritten, renumbered, or silently modified. Corrections become new evidence entries that reference what they correct.
Source Before Analysis§4
Primary source material is preserved (and hashed, where the material is a fetchable document) before analytical interpretation is written down.
Controlled Scope§4
The investigation never expands itself beyond operator-defined scope. An automated agent does not decide to investigate something new; a human does.
Human Authority§4
Only the operator (the accountable human running the investigation) determines investigation scope, case creation, evidence acceptance policy, thread closure, and investigation completion. Automation proposes; the operator decides.
Language Discipline§4
Every finding describes documented record or structural behavior, never intent, motive, or a legal conclusion (unlawful, breach, negligent) the investigation has no authority to reach. Nothing is described with more certainty than its verification status supports. MAYHEM's own remedy-demand document (Enforcement Notice) is never described as a complaint - it demands specific, binding action; it does not ask an institution to investigate itself. This applies everywhere a finding or a stage is described, not only in the document where it is stated most formally.
What this system shall never do§35
A MAYHEM-compliant system shall never: alter preserved evidence; reuse evidence identifiers; delete audit history; merge unrelated investigations; hide validation failures; modify chronology without recording the change. These constraints are invariant - not subject to case-by-case exception.

How evidence accumulates

The registers every case keeps, and the discipline behind them. §7-12, §25-27.

"No relevant change detected" is a legitimate result§7
When a pass finds no relevant source changes, it must not manufacture evidence to appear productive. Instead it records the date, the sources checked, and the honest result. A string of honest "no relevant change" outcomes is expected once a question or source is genuinely exhausted - it is not a failure to be papered over, and it is strictly preferable to inventing a finding or softening a null result into a vague restatement of what's already known.
Evidence Register§8
The investigation's primary factual record. Every item carries a permanent, never-reused identifier, its source and classification, what it establishes, and links to the chronology, contradictions and open questions it bears on. A wrong entry is corrected by a new entry that says so - never by deletion or renumbering.
Source Register§9
Every source checked - whether or not it yielded evidence - gets a permanent record, including availability notes (blocked, paywalled, since removed). A future pass can see what's already been tried, including dead ends, without re-discovering that from scratch.
Chronology§10
The factual progression of events, with confirmed entries kept distinct from pending/unconfirmed ones. Later evidence may refine an entry - add detail, correct a date - but never erase the earlier record; the correction is itself logged. Inferred dates are flagged as inferred, never presented as directly sourced.
Contradiction Register§11
Contradictions between sources are tracked as independent records, not buried in narrative: what supports each side, why it matters, what would resolve it. A contradiction is not resolved by picking the more plausible side - only by evidence actually resolving it, or by an explicit "unable to resolve" with reasoning.
Open Question Register§12
Unresolved questions are recorded permanently, not left implicit. They stay open until genuinely supported by evidence - not until a plausible-sounding but unverified answer accumulates enough repetition to feel settled.
Source classification and confidence§25-27
Every source is classified before evidence is extracted from it, and every evidence item's confidence rating reflects preservation quality and sourcing strength - never whether a conclusion is true. A plausible fact from an unfetched search-engine summary is recorded at a lower tier than the same fact confirmed against an actually preserved primary document, even describing the same underlying reality. Every search performed is logged - terms, engine, date, filters, results - so a future investigator can repeat it rather than guess what was already tried.

Automation rules

What an automated pass is allowed to do, in full, and nothing else. §6, §19, §33.

Permitted Automation§6
Every automated evidence-collection pass follows the same fixed sequence: load the case, the evidence, the chronology, the contradictions, the open questions and the threads; find where the last pass stopped; check approved sources or continue prior leads; detect genuine change (not a restatement of what's already known); preserve new source material and hash it where applicable; prevent duplicate evidence; create new entries only if something genuinely new was found; update the registers; save; stop. Nothing else occurs. A pass does not redesign the investigation, does not silently change scope, and does not delete or rewrite prior entries.
Resumption Protocol§19
MAYHEM's defining feature. Reconnecting to an investigation - a new session, a new contributor, after any gap - means loading the case, displaying the latest evidence, chronology, unresolved questions, contradictions, active threads and the latest automation result, then continuing. No reconstruction. No document rebuilding. No searching for previous work. The repository's own state is the memory - nothing relies on a human's or an AI's memory of prior sessions.
Failure Recovery§33
If interrupted at any point, the investigation resumes from the last validated state. No recovery step relies on memory - human or AI - of what happened before the interruption; everything needed is in the repository itself.

Who decides what

The audit trail for judgment calls, structural changes, and public/private discipline. §17, §29-30.

Decision Register§29
Operational and methodological decisions - as distinct from factual evidence about the investigation's subject matter - are recorded separately, in their own register: what was decided, why, by whom, and what it changes going forward. This is what lets an investigation accumulate working rules over time without re-litigating them from scratch every session.
Change Log§30
Every structural change to the repository - not just evidence additions - is logged: date, author, files affected, reason, and whether validation was completed. This is the audit trail for the repository's own evolution, distinct from the Decision Register's audit trail for investigative judgment calls.
Security§17
Private investigation records must never be described as private while actually publicly accessible. Verification status must always remain visible next to the claim it qualifies - never implied, never hidden behind a confident-sounding sentence. No interface may imply evidence certainty beyond its recorded classification.

Failure modes this exists to prevent

Not additional rules - the specific, recurring failures that motivated the rules above, named so implementers understand why they exist. Appendix A.

Manufactured evidence under pressure to look productive
An automated pass that always finds something to add will eventually pad the register with restatements or weak inferences. §7 exists specifically to make "nothing new found" a legitimate, expected, honestly-logged outcome.
AI-summary conflation
Search-engine or LLM-generated summaries can misdate old content, or blend two distinct source documents into one confident-sounding claim that neither actually supports. A striking new finding sourced only from an AI-generated summary gets checked against independently reproducible detail before it's registered - and if it doesn't hold up, the rejection and reasoning are logged, not silently dropped.
Provenance drift
Evidence extracted by an AI from a document carries a materially different confidence than a human's direct read of the same document, and this must be reflected in classification - never silently treated as equivalent.
Untrustworthy hashes
A document hash must always be the literal output of a hashing tool run against the actual preserved file - never estimated, recalled, or typed from memory. A hash that was never actually computed is worse than no hash, because it creates false confidence in integrity that was never verified.
Silent workaround of access controls
If a source is blocked - paywall, bot detection, robots.txt, an explicit organizational access policy - that is a recorded access gap, not a problem to be engineered around. Routing through the constraint dishonestly makes the resulting evidence's provenance unreliable in a way validation can't catch after the fact.
Scope creep disguised as thoroughness
Finding something interesting adjacent to the investigation's actual scope is not, by itself, a reason to register it as evidence of this case. "This is interesting" and "this is relevant to what we were asked to investigate" stay distinct judgments.
Framing drift after a correction
A language-discipline fix made in one document doesn't automatically propagate to every other place the same document or stage is described. A case's own meta description, a front-page summary sentence, or another case's copy of the same template can silently keep the old framing after the document itself has been fixed. A fix to the document is not a fix to every mention of the document - sweep for the same phrase everywhere it could recur, not only where it was first found.
Analysis re-litigating what an earlier stage already settled
A downstream stage that treats a fact as newly discovered without first checking whether an earlier stage's own record already resolved it doesn't just waste effort - it can quietly overstate uncertainty the record doesn't actually have. Read the full existing record for the stage being built on, not only the specific file that stage is nominally about.
