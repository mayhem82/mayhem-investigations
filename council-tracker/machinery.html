Technical account of the audit machinery being constructed and tested within the experiment.

Construction boundary

A council is the deliberately selected experimental subject. The machinery is not seeded with preselected matters, actors, issues, patterns, conclusions or audit targets that tell it what to find within that council’s records.

Current machinery

1 — Neutral contracts

Defines an explicit runtime source boundary, canonical URLs, SHA-256 digests and immutable preserved-source records.

2 — Acquisition boundary

Accepts an explicitly supplied HTTP(S) source, retrieves it, preserves the returned bytes and records provenance. It does not interpret the content.

3 — Neutral discovery and preservation

Discovers links exposed by the supplied source without subject keywords or predetermined record types. Same-host objects are independently preserved with provenance before interpretation.

4 — Extraction

Rechecks the preserved digest, then converts supported HTML/text objects into mechanically usable text. Unsupported binary objects remain preserved and are recorded as not extracted.

5 — Source-bound observation

Makes source text addressable as deterministic observations. An observation is source text only: not a finding, truth assessment or verification decision.

6 — Emergent relationship candidates

Compares observations using source-derived lexical overlap. Similarity creates a candidate relationship only; it does not establish a matter, causation, responsibility, importance or outcome.

7 — Source-derived identity and recurrence

Detects identifier-shaped strings supplied by the source and records recurrence across different preserved objects. Recurrence does not itself establish identity, continuity, a matter or an outcome.

8 — Evidence assembly

Assembles source observations and independently derived candidate signals into a provenance-preserving evidence graph. Every node retains its source observation, preserved object and source position. Signals remain candidates; this stage does not create matters, findings, truth assessments, responsibility assignments or verification changes.

9 — Verification boundary

Establishes a deny-by-default verification state. Evidence assembly, recurrence, similarity, internal agreement and absence of contradiction cannot promote an observation to verified. No independent verification channel has yet been admitted, so the current machinery records not-verified rather than manufacturing verification.

10 — Deny-by-default public release gate

Separates internal evidence handling from substantive public publication. Evidence-derived claims are denied release unless an explicit verified state exists. The gate cannot create findings or alter verification. Documentation about the machinery itself remains publishable.

Flow

SELECTED COUNCIL → explicit runtime source → preserve → discover → preserve each object → extract → observe → relationship candidates → recurrence candidates → evidence assembly → verification boundary → public release gate → [construction continues]

What the machinery still cannot claim

It cannot yet claim that two records concern the same substantive matter, construct a reliable lifecycle, determine responsibility, verify an outcome, sustain deeper audit paths, or publish a verified council audit finding. Those capabilities must be constructed and tested rather than assumed.

Experimental separation

This page documents audit machinery, not experimental conclusions. The Philosopher’s Stone is maintained separately as an analogy for interpreting development; its terminology is not used to define the experiment’s subject, controls, procedure or evidentiary states.

CURRENT IMPLEMENTATION BOUNDARY
Neutral foundation components remain coded but not demonstrated end to end. Analysis, findings gating and accountability attribution have now also been coded, with explicit non-promotion controls: analysis remains candidate material; unverified support cannot become a finding; and a finding cannot by itself establish an accountable actor or obligation. Advocacy, enforcement and remedy stages remain architecture-defined. No capability is marked demonstrated by the architecture contract.

New coded boundary: analysis → findings → accountability

The repository now contains three additional governed stages. Analysis groups source-linked candidate signals without converting recurrence into continuity or relationships into causation. The findings gate requires verified supporting evidence before a candidate can be promoted. Accountability attribution then remains unresolved unless separate authority and obligation evidence exists. This deliberately prevents the machinery from jumping from an interesting pattern to blame or an enforcement claim.

A structural test for this boundary has been written but is not reported as passed: the connected execution environment has not supplied execution evidence. These stages therefore remain coded-unexecuted.

First council contact becomes a machinery event

Pre-contact construction establishes the machinery entering the selected council environment. Once substantive council material is admitted, failures exposed anywhere across the architecture become developmental evidence. A correction advances the machinery only when it becomes a governed mechanism, survives retesting and later use, and transfers beyond the immediate failure rather than becoming a council-specific patch.

Accountability outputs feed the machinery back into itself

Advocacy Packages, Enforcement Notices, remedy construction and remedy verification are not terminal documents. Each is a pressure stage capable of exposing a machinery defect. Failure returns to recursive audit, correction and retained governance, creating the developmental loop now represented in the architecture.

The public layer reports this architecture; it is not execution evidence. Repository code and subsequent verified runs remain the authority for what has actually been implemented and demonstrated.
